# Адаптивный выбор набора копий, версия 0.3

Цель: сохранить своевременную доставку при ограничении числа копий и снизить
стоимость резервирования там, где дополнительные копии мало помогают.
Современность здесь связана с наблюдаемым состоянием и проверкой решений,
а не с обязательным использованием нейросети.

## Что изменилось в алгоритме

В v0.2 `risk_aware` последовательно выбирал K получателей по фиксированному
score. В v0.3 `adaptive` использует совместную историю законченных проверок
и перебирает все допустимые дополнения уже существующего набора получателей.
При 12 узлах рассматривается не больше 4096 подмножеств. Детерминированное
правило разрешает равенства. Это точный максимум заданной функции полезности;
утверждение об оптимальной маршрутизации реальной сети из этого не следует.

Новые проверки идут раз в секунду и завершаются после модельного времени
кругового обмена. До завершения результат недоступен алгоритму. Окно содержит
24 последних исхода. Совместные исходы сохраняются, поэтому два синхронно
пропадающих узла не рассматриваются как две независимые возможности.

Все нулевые векторы остаются в диагностике, но исключаются из оценки
относительного качества путей: одинаковый полный провал не помогает выбирать
между узлами. Таким образом оценка условна на наличие хотя бы одного
наблюдаемого пути. Она не является калиброванной вероятностью доставки.
Старые записи вытесняются, что позволяет реагировать на изменение каналов.

## Функция полезности

1. Для каждого узла оценивается ETA: локальная передача плюс отправка серверу
   с учётом объёма его очереди. Это приближение; резервы учитываются консервативно.
2. Множитель срока: `f_i = max(0, 1 - ETA_i / remaining_time)`.
3. Для набора S оценивается сохранение хотя бы одного пригодного пути:
   среднее `1 - product(1 - probe_i * f_i)` по информативным совместным исходам.
4. На холодном старте применяется априорная смесь независимой модели и
   консервативной модели общих групп, с весом четырёх наблюдений. Внутри
   группы используется максимум оценок, между компонентами — независимость.
5. За нового получателя платится `0.025 * (1 + source_queue + relay_queue) / max(0.2, estimated_quality)`.
6. Максимизируется оценка полезного пути минус сумма цен новых получателей.

Коэффициенты фиксированы в коде до запуска серии seed 1000–1029. Их не
подбирают отдельно под каждый сценарий. Число копий может быть меньше K.
При доступности допустимого пути первая копия обязательна для продвижения;
дополнительная выдаётся при достаточной ожидаемой пользе.

Общие метки — только априорная информация, постепенно уступающая место
наблюдениям. Неверные метки всё ещё могут испортить ранние решения. История
тоже может ошибаться при быстром изменении режима. Эти ограничения включены
в эксперименты, а не скрыты внутри интерфейса.

## Какие сведения разрешены

Оптимизатор получает идентификаторы, сообщённые метки, законченные проверки,
текущую оценку очередей, известные скорости и оставшийся срок. Он не получает
`physical_groups`, список будущих отключений, вероятность физических потерь
или будущие фазы канала. Пакет `internal/adaptive` не импортирует симулятор.
Тест `TestFutureFailurePlanDoesNotLeak` меняет будущее и сравнивает историю
решений до изменения. Полученные наблюдения также нельзя использовать задним
числом: планирование раньше времени последней записи возвращает ошибку.

Текущая очередь и локальная доступность по-прежнему наблюдаются идеализированно.
Контрольные пробы используют отдельный модельный канал, не конкурирующий за
слоты передачи данных. Их запросы и ответы учитываются в байтах у всех методов
одинаково. Это допущение нужно проверить на реальных агентах.

## Что сравнивается

| Метод | Назначение |
|---|---|
| availability | фиксированное качество без общих рисков |
| diverse | жёсткое разнесение по сообщённым группам |
| risk_aware | прежняя эвристика v0.2 |
| adaptive | новый выбор набора с историей, сроком и ценой копии |
| adaptive_independent | отключены совместная история и зависимость меток в prior; оставлены маргинальные оценки |
| adaptive_no_deadline | из полезности исключён полный ETA до сервера |
| adaptive_static | исключено обучение, оставлена априорная модель |
| random | случайный ограниченный набор |
| all | ориентир с большим бюджетом |

У методов с ограничением одинаковый пожизненный бюджет получателей для
сообщения. Потеря ACK не выдаёт его повторно. Отклонения при перегрузке
включаются в знаменатель доли доставки. В байты входят все попытки данных,
подтверждения и пробы. Это байты модели приложения, не трафик TLS/IP.

## Связь с исследованиями и граница новизны

История контактов давно используется в DTN: [PRoPHET, RFC 6693](https://www.rfc-editor.org/rfc/rfc6693.html).
Сроки жизни и отчёты о доставке описаны в [Bundle Protocol v7, RFC 9171](https://www.rfc-editor.org/rfc/rfc9171.html).
Совместные отказы и неполное знание рассматриваются в [Stock et al., 2025](https://arxiv.org/abs/2511.20241).
Учет ограничений буферов и каналов исследован в [Alhajj, Corlay, версия 2026](https://arxiv.org/abs/2410.15546).

Наш стенд не реализует эти протоколы или методы полностью и не устанавливает
превосходство над ними. Потенциальный собственный результат — исследование
малой вычислительной схемы выбора копий при ненадёжных метках, смене качества
каналов и ограниченных очередях. Новизну этой комбинации ещё требуется
проверять по литературе и независимым экспериментам.
