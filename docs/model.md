# Модель выбора и проверки

## 1. Наблюдения и решение

Для сообщения задаются бюджет дополнительных получателей K, размер B и оставшееся
время d. Кандидат должен иметь не меньше B свободных байт, оценку локальной
передачи не больше d и отчёт не старше 60 секунд. Отрицательный возраст отвергается.
Ровно 60 секунд допустимо. Отчёт считается полным снимком, задержка его доставки
во времени в этой версии не воспроизводится.

Историческую оценку можно получить функцией `HistoricalScore(s, n)`:

```text
h = (s + 1) / (n + 2)
a = h * 2^(-age_ms / 30000)
base = a / (1 + queue_fraction)
score = base / (1 + lambda * risk)
```

`availability` в JSON содержит h до старения, либо явно заданную оценку до
старения для изолированного опыта. Это показатель ранжирования, а не обязательно
вероятность. В контрольных сценариях он намеренно равен предельной вероятности
доставки. Обучение по истории контактов не реализовано; функция сглаживания
предоставлена отдельно и проверяется тестом.

Штраф относительно уже выбранных узлов:

* 0, если получателей ещё нет;
* 1, если найдено хотя бы одно пересечение известных меток;
* 0, если наборы всех участников известны и пересечений нет;
* `unknown_penalty`, если пересечение не доказано, но сведения неполны.

Даже при `risk_known=false` наблюдаемое пересечение имеет приоритет.
После каждого выбора множество получателей обновляется. При равных оценках
выбирается лексикографически меньший ID. Входной порядок узлов не влияет на
детерминированный выбор. Внутренний список сортируется отдельно от списка вызывающего кода.

`diverse` сначала выбирает минимальный штраф (0, неизвестность, 1), затем
максимальную базовую оценку. Это явное определение контрольного правила для
неполных меток; в примерах все метки известны. `all` намеренно игнорирует K,
но использует те же фильтры допуска. Остальные стратегии не превышают K.

## 2. Физический мир

Все первичные события независимы: доступность каждой группы и условная доставка
каждого узла. Узел доставляет сообщение, только если доступны все его физические
группы и произошло его собственное событие доставки. Следовательно, результаты
узлов с общей группой уже зависимы. Несколько общих причин допускаются через
несколько записей `actual_groups`.

Наблюдаемые метки не проверяются на совпадение с физическими группами: иначе
невозможно исследовать ошибки конфигурации. `selector` вообще не получает
`actual_groups`, вероятности первичных событий или их будущие исходы.

Начальные копии уже размещены. Источник до срока не имеет прямого контакта
с сервером; сервер доступен. Собственная копия источника не даёт дополнительного
успеха в данной постановке. Событие «группа доступна» означает доступность,
достаточную для доставки в пределах срока, а не просто включённое питание.

## 3. Точный расчёт

Для N первичных событий перебираются 2^N состояний. Вес состояния равен
произведению p для произошедших событий и (1-p) для остальных. Суммируются веса
состояний, где хотя бы один выбранный узел доставил сообщение.
Используется рациональная арифметика, а округление выполняется только при выводе.

Для A и B с общей группой вероятности 0.8 и условными вероятностями 0.9 и 0.85:

```text
P(A или B) = 0.8 * (1 - 0.1 * 0.15) = 0.788
```

Для независимых итоговых доставок A (0.72) и C (0.56):

```text
P(A или C) = 1 - (1 - 0.72) * (1 - 0.56) = 0.8768
```

При ошибочных метках алгоритм может выбрать физически зависимые A и B.
Тогда расчёт должен вернуть 0.788, хотя алгоритм считает их разнесёнными.

Для `random` точное значение усредняется по равновероятным K-подмножествам.
Если в состоянии успешны m из n допустимых узлов, условная вероятность успеха
равна `1 - C(n-m,K)/C(n,K)`; при K=0 она равна нулю.

## 4. Случайные опыты и интервалы

Один trial представляет новое сообщение с заново разыгранным состоянием мира.
Нет временной корреляции между сообщениями и длительности отключений.
Для каждой стратегии используются одни и те же исходы первичных событий.
Случайный выбор имеет отдельный поток RNG и не изменяет поток отказов.

Для сценария с индексом j и прогона i seed равен `base_seed + j*1000003 + i`.
В каждом прогоне вычисляется доля доставленных сообщений. Затем выполняются 2000
bootstrap-перевыборок прогонов с возвращением. Из распределения средних берутся
приблизительные 2.5-й и 97.5-й процентили. Для разности методов сначала вычисляется
парная разность на каждом прогоне, затем бутстрэпятся эти разности.

Интервалы отражают неопределённость Монте-Карло при фиксированных входных
вероятностях. Они не учитывают неопределённость самих исходных предположений.
При увеличении числа trial интервалы должны сужаться около точных результатов.
Это проверка симулятора, а не доказательство эффективности на реальной сети.

## 5. Метрики и границы

Основная метрика: доля сообщений с доставкой до срока по заданным первичным
событиям. `placement_payload_bytes_per_message` означает B умножить на число
дополнительных получателей; собственная копия источника не включена.
Все начальные размещения считаются успешными и выполненными до отказа.

Статическое `queue_fraction` меняет оценку узла, но не является моделью очереди.
`free_bytes` и `transfer_millis` только фильтруют допустимость выбора. Нет
передачи между ретрансляторами, частичной записи, ACK, подписей, mTLS, потери
диска, отзыва сертификатов, служебного трафика или измерения задержки.

Следующее исследование должно добавлять механизм времени, а не приписывать
этим статическим результатам характеристики реального сетевого прототипа.
