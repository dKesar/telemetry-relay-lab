# telemetry-relay-lab

Экспериментальная модель выбора ретрансляторов для диагностической телеметрии.
Основной язык: Go. Внешних Go-зависимостей нет.

## Какую задачу решаем

У источника есть сообщение и бюджет на две дополнительные копии. Два хорошо
доступных узла могут зависеть от одной точки доступа или линии питания.
Размещение обеих копий на них не защищает от отказа общего оборудования.
Третий узел может иметь худшую связь, но другую общую зависимость.

Алгоритм выбирает между качеством отдельных узлов и разнесением копий.
Исследовательский вопрос: когда такой компромисс полезен, а когда он ухудшает
доставку по сравнению с более простыми правилами?

## Что уже реализовано

* Последовательный выбор получателей с учётом доступности, очереди и общих рисков.
* Проверка свободного места, срока передачи и свежести отчёта.
* Различение неизвестных меток и подтверждённого отсутствия общей зависимости.
* Четыре стратегии с одинаковым бюджетом копий и ориентир `all` с большим бюджетом.
* Точный перебор первичных событий с рациональной арифметикой `math/big.Rat`.
* Сравнение стратегий на общих случайных исходах и независимых seed по прогонам.
* CSV с результатами каждого прогона, парными разностями и bootstrap-интервалами.
* Тесты расчётов, входных данных, граничных условий и воспроизводимости.

Это версия 0: снимок уже размещённых копий. Контакты, длительности отказов,
повторы, изменение очередей во времени и сетевой обмен пока не моделируются.
Срок доставки здесь включён в заданную вероятность события «доставлено до срока».
Оценка времени размещения используется только как фильтр допуска узла.
Из этой модели нельзя получить измеренные latency, throughput, CPU реального
агента или время восстановления сети.

## Запуск

Нужен Go 1.22 или новее. Установка: https://go.dev/doc/install

```bash
git clone https://github.com/dKesar/telemetry-relay-lab.git
cd telemetry-relay-lab
go test ./...
go run ./cmd/relaylab exact
```

Первая команда программы выводит CSV в терминал с точной дробью и десятичной
вероятностью для каждого сценария и стратегии.

Случайные эксперименты, 30 независимых прогонов по 10 000 снимков на сценарий:

```bash
go run ./cmd/relaylab experiment -seed 42 -runs 30 -trials 10000 -out results/paper-42
```

Каталог назначения должен быть новым. Программа не перезаписывает предыдущие
эксперименты. Для следующего запуска задайте другой `-out`.

Файлы результата:

| Файл | Содержание |
|---|---|
| `config.json` | Исходная конфигурация без изменений |
| `manifest.json` | Seed, число прогонов, SHA-256 конфигурации, версия Go и платформа |
| `exact.csv` | Точная вероятность каждой стратегии |
| `runs.csv` | Результаты всех прогонов, число копий и байты размещения |
| `summary.csv` | Средние, интервалы и парные разности относительно `availability` |

Дополнительно сохраните SHA коммита (`git rev-parse HEAD`) вместе с результатами.
В `examples/reference/` сохранены результаты проверочного запуска этой версии.
Пример не является измерением прототипа на реальном оборудовании.

## Стратегии

| Имя | Правило |
|---|---|
| `random` | Равновероятный набор K разных допустимых узлов |
| `availability` | Максимум доступности с поправкой на возраст отчёта и очередь, без штрафа за общий риск |
| `diverse` | Сначала меньший риск относительно выбранных узлов, затем доступность с поправками |
| `risk_aware` | Мягкий штраф за общий риск с коэффициентом `lambda` |
| `all` | Все допустимые узлы; сравнение с отдельным, большим бюджетом |

Это собственные простые контрольные правила. `random` не является полной
реализацией Spray and Wait; остальные имена также не обозначают реализации
PRoPHET или RAPID.

## Контрольный результат

Точные вероятности в процентах, округлённые до двух знаков:

| Сценарий | availability | diverse | risk_aware | all |
|---|---:|---:|---:|---:|
| Общий отказ A и B | 78,80 | 87,68 | 87,68 | 90,67 |
| Независимые отказы | 91,04 | 87,68 | 87,68 | 96,06 |
| Слабая альтернатива C | 78,80 | 74,24 | 78,80 | 80,50 |
| Ошибочные метки | 78,80 | 78,80 | 78,80 | 90,67 |

У первых трёх стратегий две дополнительные копии; у `all` здесь три.
При размере сообщения 512 байт это 1024 и 1536 байт первоначального размещения.
Собственная копия источника и запись сервера в эту метрику не входят.
Это не полный сетевой трафик: TLS, квитанции и повторы ещё не реализованы.

Вывод ограничен моделью: общий риск иногда полезно учитывать, но неверные
метки и неоправданный штраф могут убрать выигрыш. Первая строка не доказывает
превосходства мягкого штрафа над простым разнесением: результаты там совпадают.

## Как менять эксперимент

Скопируйте `configs/paper.json`, измените параметры и передайте путь:

```bash
go run ./cmd/relaylab experiment -config configs/my-scenarios.json -out results/my-run
```

* `observed` содержит только доступные алгоритму сведения.
* `actual_groups` описывает реальные зависимости и доступно только испытателю.
* `conditional_delivery` задаёт вероятность своевременной доставки при доступности
  всех реальных групп данного узла.
* `up_probability` задаёт вероятность доступности группы в пределах срока.
* Вероятности записываются строками, например `"0.8"` или `"4/5"`, для точного расчёта.
* `lambda = 0` отключает штраф за риск и даёт выбор `availability`.
* `risk_known = false` означает неполные сведения; `risks = []` вместе с
  `risk_known = true` означает известное отсутствие меток в данной модели.

Чтобы изолировать влияние ошибочных меток, меняйте `observed.risks`, оставляя
физические параметры прежними. Для проверки качества альтернативы меняйте
`conditional_delivery` у C и отдельно задавайте, что о ней знает алгоритм.
В этой версии для точного перебора действует лимит 16 первичных событий
(количество групп плюс количество узлов).

## Проверки и производительность функции выбора

```bash
go test -race -cover ./...
go vet ./...
go test ./internal/selector -bench . -benchmem
```

Бенчмарк измеряет только функцию выбора на текущем компьютере. Он не измеряет
пропускную способность распределённой системы. Конкурентность намеренно не
введена в маленький симулятор: последовательный прогон легче воспроизводить.
Go-агенты и ограниченные пулы goroutines появятся на сетевом этапе.

## Где что находится

```text
cmd/relaylab/          CLI и экспорт результатов
internal/selector/    правило выбора по наблюдаемому снимку
internal/model/       конфигурация и независимые первичные события
internal/experiment/  точный расчёт, случайные прогоны, статистика
configs/paper.json    четыре контрольных сценария
docs/model.md         математическая постановка и ограничения
docs/roadmap.md       переход к модели времени и сетевому стенду
```

Научная новизна и универсальное преимущество алгоритма не заявляются.
Репозиторий предназначен для проверки гипотез и получения воспроизводимых
результатов перед реализацией сетевого прототипа.
